# Live behavior and context contract

Audited against OpenAI's GPT-Live prompting, delegation, conversation, and WebRTC guides on 2026-10-07. The application owns task orchestration, editor targeting, tools, and proposal acceptance. GPT-Live owns listening and spoken delivery. A fast backend does not by itself guarantee a responsive pair-programming experience.

## Speaker and backend prompts

`extension/src/prompts.ts` keeps these separate. The speaker has concise conversation instructions and explicit **Backchannel policy**, **Interruption policy**, and **Delegation policy**, including the documented labels for backend capabilities and when to delegate. It waits for grounded results, avoids narrating code, and treats navigation as context rather than a request. The backend has detailed instructions for evidence gathering, current user intent, incomplete speech, tool scope, target ambiguity, and structured results.

Tool execution is followed by a separate schema-constrained formatting request when tool calling ends in prose. The backend returns one canonical summary, status, and at most one exact replacement or cursor insertion. The same summary supplies the spoken answer; there is no separately generated speech field that can contradict it. Application-confirmed preview/acceptance facts override older transcript references. Provider private reasoning is never forwarded.

`pairCode.reasoningEffort` defaults to `auto`: the host calls OpenAI's public-beta Decisions API with `gpt-6-luna` to classify the latest task as none/low/medium/high, then maps that choice to the foreground Cerebras request. The classifier cannot execute tools or grant permissions. Classification has a four-second deadline and falls back to medium on refusal, low confidence, missing access, or network failure. Manual effort settings bypass it. Complexity is separate from the assistance slider. Qwen final formatting and inline predictions use none; Cerebras parsed reasoning is discarded. Together research effort comes from the selected profile, independently of foreground routing.

Backend output allowances are 32,768 tokens on Cerebras and Together, including reasoning. Cerebras uses an allowance valid on free and paid accounts; paid accounts can support higher output, which is not currently requested. The context estimate targets Cerebras’s 131,072-token window or a conservative 1,000,000-token Together research window, with output room reserved; an explicit context-limit rejection retries against 65,536 for smaller accounts. Near the provider window, oldest complete conversation/tool exchanges are omitted, retaining instructions, the captured target and latest user intent; the model is told to re-read missing evidence. This is an estimate, not the provider tokenizer or a guarantee of full dependency knowledge. The old 56-KB payload rejection and conversation-count/fragment-length caps are gone. Inline predictions retain a separate 1,024-token allowance for latency.

Oversized previews and output exhaustion receive internal feedback to generate one coherent smaller piece. Partial tool calls are never executed and code is never truncated into a preview. After recovery is exhausted, the result truthfully says no preview is ready, without a sidebar generation error or a claim of completed work.

## Session and message lifecycle

1. The extension host creates `/v1/live/sessions` with `gpt-live-1`, client delegation, `store: false`, and the WebRTC offer. Keys stay in the host. The panel uses `oai-events` and waits for `session.started`; it does not send a second start event.
2. A reconnect seeds bounded prior user/assistant conversation and current editor metadata in `session.input`, using text content parts. This is final conversation content, never private reasoning. Each new session has its own timeline and event deduplication.
3. Raw transcript fragments retain role, offsets, and session identity. Backend retrieval cuts off raw fragments before grouping them, so a later continuation cannot leak into an earlier delegation. The sidebar does not display transcripts. Raw fragments remain in host history and the local trace. A 1.8-second gap is only a context heuristic, not proof of a completed turn.
4. A delegation event provides ID, target, and offset, not a task prompt. The host builds the task from transcripts and context. A newer task or explicit cancel aborts the older backend request and ignores late results. Audio interruption alone does not cancel a coding task.
5. Quiet focus and task-lifecycle facts use `session.thinking.append`. Routine per-tool progress remains in the sidebar and local trace; it is not appended to the speaker. Speech-worthy backend facts use `session.commentary.append`, retaining the delegation ID (or null for application-initiated updates). Every append is bounded conservatively to 480 UTF-8 bytes, below the documented 500-token cap. Code stays in the editor. Pairing-style changes use trusted `session.instructions.append` updates with `delegation_id: null`; source and web content must never be inserted there.
6. Client event IDs correlate acknowledgments and errors. Context acknowledgment timestamps place delivered editor metadata on the Live timeline. Acceptance is not proof of audio playback. Input audio must remain active, including silence, for the timeline to advance; the synthetic test initially stalled until it supplied a continuously active source. Uncertain appends are not automatically retried. Typed requests go directly to the backend and their quiet voice mirror explicitly says the application is already handling them.
7. Mute disables the local track immediately. Unmute enables it only after the matching acknowledgment. A failed/timed-out control closes the session. Muting retains the connected session and its usage. Disconnect immediately stops capture/playback, sends `session.close`, and drains final events for up to five seconds; missing final usage is labeled unconfirmed. Late events from an old peer cannot affect a new peer.

## Editor targeting

The backend receives an unsaved buffer window, document URI/version, absolute cursor and selection offsets, viewport, diagnostics and recent paths. Speech targets are captured locally at the first input transcript fragment, independently of delayed Live acknowledgements. Later fragments retain that target; a subsequent human response after assistant speech captures a fresh target. Typed requests capture their target when submitted. This is a transcript-arrival heuristic, not precise audio-start timing.

Switching files or opening the terminal during generation does not cancel the task, invalidate an otherwise unchanged target, or force a target question. A ready preview remains associated with its original document and is rendered when that document is active, without stealing focus. Acceptance still requires the exact captured URI, version, offsets and old text, so a genuine human edit invalidates the old draft.

Live context now includes cursor column and the current code line, marked as untrusted reference data. Rapid typing updates still wait for playback/editing to settle. Spoken input requests an urgent fresh update; urgency survives an older pending acknowledgement. On "done/continue", the speaker is instructed to delegate for the latest buffer instead of repeating a remembered line. Editor updates alone never advance coaching.

## Native tools and limits

| Capability            | Current implementation                                                                                                                     |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| Workspace map / paths | `workspace_overview`, `find_files`; shallow directory maps and streamed, scoped pages (80 paths by default, up to 200)                     |
| Source retrieval      | `read_file` uses unsaved buffers, 400 lines per call; `read_files` reads up to eight ranges concurrently (80 lines / 2,500 bytes per file) |
| Literal search        | `search_text`; native ripgrep across eligible scoped text, 40 matches per page, with unsaved overlays and match offsets                    |
| Code relationships    | `symbol_usages` invokes installed language services for definitions, references, incoming/outgoing calls; provider coverage varies         |
| Feedback              | `diagnostics`, file-scoped `git_diff` (fixed command, no external diff/text conversion)                                                    |
| Public documentation  | Optional Firecrawl `web_search` and `fetch_page`; URLs, retrieval time, and source status returned                                         |
| Edits                 | One captured-target native inline preview, including empty files; Accept/Reject CodeLens and ⌘Enter; separate insertion predictions        |

The fixed seven-round/twelve-tool limit is removed. Research can continue through distinct lookups until it answers, is cancelled, or reaches the configurable task deadline (`pairCode.backendTimeoutSeconds`, default 600; 0 disables the total deadline). Provider calls retain a 120-second network deadline; Firecrawl has 60 seconds. Two consecutive identical cached tool calls finalize a stalled loop. An explicit local-only or no-web request removes web_search and fetch_page from both main-agent and explorer tool availability; a hallucinated unavailable call cannot invoke them. Tools remain pageable with explicit coverage rather than uploading an entire repository. Sharing/trust/path checks still apply at execution. Public fetch allows ordinary HTTPS pages through Firecrawl, and all retrieved content is untrusted evidence. Private code must not enter public web queries.

`delegate_to_agents` exposes every enabled user-defined worker by ID, name, description and default execution mode. The backend chooses by relevance; neither model effort nor a fixed role name automatically selects a worker. A batch contains up to eight independent jobs; four execute concurrently per pairing window and up to 32 can be active/queued. Each job has an isolated context, immutable definition snapshot and separate controller. Foreground jobs return reports in the tool result; background jobs return IDs and publish completion independently. The same definition can run multiple times concurrently. `agent_run` inspects a full report or stops a specific job. It is not cached as a source lookup.

Workers receive only their delegated task, explicit scope and active-file locator; source is fetched through permitted tools. They receive only assigned, globally enabled tools, with web tools only when the actual human requested external evidence. Shared workers use live source/discovery/reference/index tools; memory tools can be assigned explicitly. Isolated-worktree workers can use apply_patch and individually approved command tools, returning multi-file changes for human review. Recursive delegation is not exposed to workers. Arbitrary user-defined roles are supported within these assigned capabilities. Main retains its captured single-file inline proposal flow; isolated implementations use Review changes with current-buffer and assistance checks. Reports are interpretations; they must be rechecked against current code before an edit. Compact report excerpts return by default (2,000 characters with an explicit truncation flag and full-report tool), keeping worker transcripts/source bodies out of the parent context.

Hybrid indexing and reusable local research briefs are now implemented (see the later retrieval updates). Automatic complete service/dependency graphs, runtime tracing, arbitrary command execution, test runner and MCP client remain unimplemented. Cross-service effects require evidence from contracts, callers, or explicit service metadata. An empty reference search is not proof of no downstream impact.

## Adjustable pairing style

The continuous sidebar **How much Pair does** slider moves in steps of 1 and uses a linear allowance of `level * 10` generated changed lines per preview (unchanged replacement lines do not count). It persists `pairCode.assistanceLevel` (0–100) and defaults to 25. It controls pacing and the amount of proposed code independently of backend reasoning effort.

| Value | Behavior                                                                                                                                                                                                              |
| ----- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 0     | Coach one exact line or concrete action, explain why, and wait for the human to ask for the next step. Voice guidance only: no backend edit proposals and no inline completion requests, including manual invocation. |
| 25    | Explain one small step. Explicit write/change requests can produce a preview with at most 250 generated changed lines.                                                                                                |
| 50    | Build one logical piece together, with previews of at most 500 generated changed lines.                                                                                                                               |
| 75    | Draft one coherent section, with previews of at most 750 generated changed lines, then pause for review.                                                                                                              |
| 100   | Draft the requested implementation as one focused preview, then ask what the human wants clarified.                                                                                                                   |

Learning questions receive guidance at every setting unless the human asks for generated code. Existing preview acceptance and rejection remain unchanged. Larger replacements count their entire replacement text toward the budget: the backend must select a narrower safe anchor or provide guidance, never truncate code to fit. A scope violation gets one bounded repair; a second violation stops without a preview. In guide mode, the strict provider schema excludes proposals and permits zero edits, and application validation independently rejects edits even if a custom provider ignores that schema.

The voice model gets the style at session creation and again on `session.started` to cover settings changed during connection. Changing it cancels pending inline predictions while preserving backend research. The local policy updates immediately; a concise behavior update is coalesced and queued until playback/transcript activity is quiet, then sent through `session.instructions.append`, without reconnecting. A late backend preview that violates the new assistance level is suppressed. Switching to 0 dismisses any existing preview so the editor returns to voice-only guidance; other settings retain existing previews for human review. The next backend request captures the new style, and task-revision checks ignore late results from canceled work. No automatic next task is launched just because the slider or editor context changed. OpenAI documents that append acknowledgment confirms timeline acceptance, not that the model has acted on the instruction: [Managing GPT-Live sessions](https://developers.openai.com/api/docs/guides/live-conversations).

### Shared computer index

`IndexService` enforces window trust/context policy and overlays dirty buffers. `SharedIndexClient` connects to the local daemon; `SharedIndexCoordinator` scans saved sources and coalesces work by canonical checkout; `CodeIndex` stores all registered checkouts in one shared Turso schema. Database row identity includes checkout plus relative path, with repository and service metadata. RPC search always forces an authorized checkout before applying repository/service/path/language filters and ranking. Retrieved source is revalidated by both daemon and window.

The store is `~/.zen/code-index/shared-v2/` across launch profiles. The connection token and directory are private to the OS user. RPC is raw framed JSON over authenticated `127.0.0.1` TCP, with version checks, bounded frames, cancellation and bounded progress buffering. A deterministic per-store port provides kernel-enforced ownership: only the process that binds it opens Turso. Losers connect to the existing owner. A conflicting foreign endpoint fails authentication/version checks instead of opening a second database. There is no shared-service filesystem owner lock to orphan. Crashes release the endpoint; clients reconnect, re-register their roots and resume source reconciliation. The daemon is bundled beside the native Turso module and grammar assets and runs through Electron's Node mode.

Roots are registered only by trusted windows with context sharing/indexing enabled. Duplicate subscribers share one scan; at most two roots index concurrently. Clients send saved-file change notifications; unsaved source is never persisted in the shared database. A new idle/reopened root rescans permitted source, reuses hashes and removes deleted/ignored rows. Root registrations are connection-scoped; a window cannot query closed/unregistered roots merely because their rows remain in the store. Revoking or closing the last subscriber aborts ingestion, discards its in-memory credentials and leaves persisted vectors available for a future authorized reopen. With no connected clients the daemon shuts down after 60 seconds.

Migration is rebuild-only: old profile `indexes` directories are retired and deleted when no recorded live owner holds them. A missing/dead PID does not block retirement; known live owners defer cleanup to a subsequent refresh or startup. Personal memory, session traces, API keys, settings and working copies are outside this cleanup. Old rows are never imported; current ignore/private/realpath policy determines the rebuilt source set. Database layout is versioned independently of the unchanged OpenAI small / 768 embedding namespace.

### Deferred embeddings and reusable exploration context
